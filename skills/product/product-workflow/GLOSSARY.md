# Word list

Product teams use special words. This list gives the meaning of each word in
simple English. You do not have to use these words. If a skill uses one, the
skill also gives the meaning.

| Special word | Meaning |
| --- | --- |
| Artifact | A document. Each stage makes one markdown file. |
| Gate | A condition that must be true before you go to the next stage. Some gates need a "yes" from the user. |
| Bet | The one thing the team decides to build next. It is a bet because it can fail. |
| Opportunity | A problem, a need, or a pain of a real user. It is not a feature. |
| Outcome | A change in what users do. For example, more users complete setup. |
| Output | The work the team ships. Much output does not mean much value. |
| Appetite | The time the team accepts to spend. Set the time first. Then design the solution to fit. |
| Estimate | A guess of how long the work takes. This is not the same as appetite. This loop does not use estimates. |
| Fat-marker sketch | A rough sketch. It is good enough to judge the idea. It is not good enough to build from. |
| Rabbit hole | A small detail that can take many weeks if nobody makes a decision early. |
| Non-goal | Something the team can build, but decides not to build. Write it down to keep the decision. |
| North star | The one main number that shows if users get real value. |
| Input metric | A smaller number that a team can move in one week. It must move the main number. |
| Guardrail | Something that must not become worse while the team makes the win. |
| Leading indicator | An early signal. It moves in days. |
| Lagging indicator | The confirmation. It moves in weeks or months. |
| Vanity metric | A number that looks good and changes no decision. Usually a count with no total. |
| Falsifiable | Written so that a person can show it is false. "More engagement" is not falsifiable. "Setup completion from 40% to 55% in 6 weeks" is falsifiable. |
| Assumption | Something the team accepts as true with no proof. It is dangerous if it is important and has no proof. |
| Fake door | A real button for a function that does not exist. Use it to count how many users click. |
| Concierge test | The team gives the value by hand before it builds the software. |
| Spike | A short study with a time limit. It answers one engineering question. |
| Problem space | Talk about user problems. |
| Solution space | Talk about what to build. Do not rank problems and solutions in one table. |
| RICE | A score formula: Reach × Impact × Confidence ÷ Effort. |
| ICE | A faster formula: Impact × Confidence ÷ Effort. |
| Kano survey | Two questions per feature. They show which features users expect and which features make users happy. |
| Cost of delay | What the team loses for each week it does not ship. |
| Now / Next / Later | A roadmap with no dates. The groups show how sure the team is. |
| Job to be done | The result the user wants. For example, "I want to look prepared", not "I want a dashboard". |
| Four forces | Why a user changed tools: what pushed the user away, what pulled the user in, what made the user afraid, and what kept the user in place. |
| Mom test | An interview rule. Ask about the life of the user. Do not ask if the user likes your idea. |
| Verbatim | The exact words of the user. Copy them. Do not make a summary. |
| Table stakes | All competitors have it. If you do not have it, you lose. If you have it, you win nothing. |
| Differentiator | A reason a user selects your product and not another product. |
| PRD | Product Requirements Document. It gives the problem, the users, and the definition of done. |
| PR/FAQ | A document format. Write the launch announcement first. Then answer the hard questions. |
| Acceptance criteria | The list of conditions that show a requirement is complete. |
